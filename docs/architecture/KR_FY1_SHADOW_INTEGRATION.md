# KR FY1 Shadow Integration

REV40-R1 is an explicit KR8-only source and shadow-model opt-in. Default all22
acquisition, model topology and production packet behavior are unchanged.

The official KIS output3 owner retains its accepted raw/10 scale, exact security,
fiscal period, FY1 and research-snapshot semantics. A positive qualified EPS
permits an unadjusted latest completed-session close and the six-variant exact
share-unit action guard. Current FY1 fPER is the existing Decimal-derived receipt,
not the provider research PER. Missing and nonpositive EPS remain separate states.

`kr-fresh-fy1-valuation-view-v1` binds those immutable receipts to the native
current PER/PBR view, new acquisition time, plan and source corpus. The typed
`kr-fy1-valuation-calibration-context-v1` grants only NewBuyer/Holder calibration
refs. Core and Pass A never receive forward valuation. Overall direction and
business evidence refs cannot consume it. The five metric families remain
independent; there is no target price, NTM or consensus interpretation.

`accepted-kr-forward-valuation-message-v1` deterministically rebuilds the accepted
detailed base and substitutes three bound FY1 rows for its generic fPER row.
PER/PBR and all other rows retain their original ownership. Exact sender text
must reproduce from the typed plan; appending or changing prose fails audit.

The KR proof controller preserves the existing three KR batches per stock stage,
plus one required supporting KR Market call: ten logical calls maximum. Official
signed-in Sol/xhigh, 1200 seconds, zero retries/fallback/judge. All source gates,
offline replay twice, source-only ZIP seal and exact code/host qualification
precede calls. US provider/model/message scope is zero. The eight stock payloads
are captured locally; supporting KR Market capture is separately counted.

The user's storage amendment allows the task-specific 10-GiB KR floor instead
of the broad 12-GiB acquisition floor. It does not change production defaults,
permit evidence deletion or bypass the remaining KR/model disk guards.

No Telegram, operating DB, warning, notification, scheduler, main merge, push,
deployment, restart or broker mutation is permitted by this integration.
