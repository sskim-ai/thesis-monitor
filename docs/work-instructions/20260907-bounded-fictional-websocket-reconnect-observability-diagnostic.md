## 0. Scope and objective

This is a narrowly bounded runtime-observation experiment, not another real-issuer ownership proof.

Use the latest offline closeout as the completed baseline. Execute **at most three fictional Directional Core model subprocess calls**, with no wrapper retry, to observe whether a WebSocket disconnect is followed by recovery, explicit termination, or watchdog timeout.

The task must not:
- call the model for any real issuer, select a real holdout, or resume historical B/C;
- change investment prompts, decision thresholds, schemas, source-sufficiency policy, composer or renderer semantics;
- change the selected model, reasoning effort, timeout, CLI binary, transport protocol, reconnect behavior or process lifecycle;
- resume scheduled monitoring or send any production message;
- add paid data services, a free-API entitlement gate, or a broad provider audit.

A three-call PASS means only that the observed failure did not recur within this small experiment. It does not establish production reliability or complete FIRST/A/B/C generalization.

The task has one diagnostic question:
> Under the unchanged transport and a fixed fictional four-subject request, what observable runtime sequence occurs when repeated calls use distinct sessions and state namespaces?

This does not recreate all 16 successful contexts preceding the historical failure. Do not imply that it does.
